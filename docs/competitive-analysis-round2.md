# 第二轮竞品差异与用户痛点（2026-10）

> 目标用户：中文办公人群（定义见 `CONTEXT.md`）。
> 竞品圈：国际直接竞品 + 中文同类 + 番茄/专注、系统专注、手表等邻近替代。
> 方法：公开证据优先（GitHub issues、App Store 评论、中文社区），Morrow 现状以代码为准；证据强度逐条标注。
> 上轮基线：`docs/competitive-analysis.md`（基础能力补齐）。

## 结论先行

1. **中文办公人群最痛的不是「提醒不够」，而是「在该安静的时候被看见、被打断」。**
   会议与共享屏幕是第一痛点；Morrow 的桌宠与全屏遮罩还会把「打断」升级成「被同事看见」（机制推导，见 P1）。
2. **第二痛点是提醒时机。** 固定排程到点即弹，正在打字或拖拽时尤其刺眼；Morrow 的强提醒默认全屏，放大了这个问题。
3. **第三是坚持不下来。** 跳过成习惯、看不到长期效果；Morrow 有今日统计、连续天数和宠物生长，但没有 7 天/周报，也没有对连续跳过的温和反馈。
4. **第四是差异化用不上。** AI 场景需要自备 API Key，非技术用户很难在第一次打开时得到一套可用计划；中文同类又普遍是固定计时器。
5. **Morrow 已经具备竞品没有的组合：** 本地优先、中文会议应用识别、暂停原因可见、顺延不补发、多屏强提醒、桌宠。不要为了追平而引入摄像头、严格模式或云端账号。

## 二、用户痛点证据

### P1 会议 / 共享屏幕：被弹窗，甚至被看见

**证据（强）**

- Stretchly #1479「Pause when sharing screen」（2024，closed）：用户明确要求共享屏幕时暂停。
- Stretchly #969「Pause while camera is in use」（2021，open）：浏览器会议无法靠应用名单识别。
- Stretchly #1120（2022，closed）：Teams 会议中仍继续弹；原文 “breaks are not paused they continue to run”。
- Stretchly #355「Full screen applications disable Stretchly」（2019，open）：全屏应用被休息通知打断或最小化。
- 中文同类公开页普遍没有会议 / 共享屏幕识别；用户只能静音或手动暂停（App Store 评论与社区，样本有限）。

**Morrow 现状**

- 会议应用名单覆盖腾讯会议、飞书、钉钉等 7 家；全屏识别可兜底一部分浏览器会议。
- 但桌宠、强提醒是独立置顶窗口，没有「共享时隐藏 / 排除捕获」；也没有一键演示模式。
- 强提醒出现时，宠物气泡不会自动让位（`frontend/src/views/Alert.vue` 的注释明确不为强提醒隐藏宠物）。
- 结果是：即使提醒被暂停，桌宠本身仍可能出现在共享画面里。这是机制推导，不是用户原话。

**机会**

做「演示模式」：手动进入 + 会议 / 全屏时建议进入 + 系统级捕获排除。竞品没有桌宠，也就没有这项能力；这是 Morrow 专属的差异化。

### P2 时机僵硬：打字 / 拖拽时被全屏打断

**证据（强）**

- Stretchly #189「Stop disturbing」（2018，closed）：原文 “Sometimes a popup appear in the middle of writing a text. I don't want to lose the concentration, so I stop typing...”（[issue](https://github.com/hovancik/stretchly/issues/189)）。
- LookAway 官方把「 waits for the right moment」作为卖点，说明「时机」本身就是用户可感知的价值。

**Morrow 现状**

- 固定排程到点即弹；强提醒默认开启且铺满所有屏幕。
- 只有「空闲暂停」，没有「正在输入时顺延」；用户在专注打字时反而最容易被打断。

**机会**

做「自然停顿顺延」：检测到最近有键鼠输入时，最多顺延 60 秒，等到用户停手再提醒；宠物可以承担「等你停下」的状态。成本低，和现有空闲检测同源。

### P3 识别不可靠：浏览器会议 / 全屏视频

**证据（中强）**

- Stretchly #969、#1479：浏览器会议、共享屏幕是名单识别的盲区。
- LookAway 用摄像头 / 麦克风判断会议，存在漏判（只听会、关麦）与误判（录音）的取舍（厂商文档自述）。

**Morrow 现状**

- 原生 7 家会议应用 + 全屏兜底；浏览器会议只能靠全屏，非全屏网页会议会漏。
- Windows 上专注 / 日历两路静默缺席；全屏视频可能被当成「该暂停」（这个方向通常安全，但会漏掉非全屏网页会议）。

**机会**

多信号融合 + 手动纠正 + 暂停原因可见；不承诺 100% 识别。可以把「刚才该暂停」做成一个本地反馈入口，让用户教一次，而不是让用户找设置。

### P4 提醒疲劳：跳过成习惯，工具变成噪音

**证据（中强）**

- Stretchly #1366「Ability to pause Stretchly via menubar in strict mode」（2023，closed）：严格模式下用户需要紧急暂停；讨论里反复出现「总是跳过休息」的习惯。
- 中文社区有「工具要么太吵要么没用」的说法（App Inn 讨论，样本小）。

**Morrow 现状**

- 有完成 / 跳过 / 推迟；没有严格模式（这是正确的）。
- 但没有对连续跳过的温和反馈：用户连续跳过三次，系统仍然按原节奏继续弹。

**机会**

做「节奏自适应」：连续跳过 / 推迟时，宠物问一句「现在不方便？暂停 30 分钟 / 降低频率 / 继续」，由用户拍板；不自动隐藏、不做强制。与严格模式相反，符合温和陪伴的定位。

### P5 看不到长期效果

**证据（中）**

- Stretchly #266「History and Timeline of Breaks」（2018 至今 open）。
- 中文 App Store 评论希望有小时统计（久坐时间、喝水时间），说明「提醒之后发生了什么」是共性需求。

**Morrow 现状**

- 今日统计、每条提醒的连续达标天数、宠物五档生长。
- 没有 7 天趋势 / 周报，也没有跨提醒的复盘；用户只能看到「今天」。

**机会**

做「轻量周报」：7 天完成 / 跳过 / 推迟、连续天数、宠物生长，长在菜单栏与宠物上；不做独立仪表盘，不做云端。

### P6 上手 / 配置 / AI 门槛

**证据（中；部分是产品事实）**

- 产品事实：AI 计划需要 OpenAI 兼容 Key，默认端点是 DeepSeek（`internal/ai/ai.go`）；没有场景模板或首次引导。
- 中文同类以固定计时为主；少数派 / App Inn 有用户自写提醒工具，以及「为了一个提醒站起来每月付费，总觉得哪里不对」的吐槽。
- BYOK 门槛是非技术用户的推断，尚无直接访谈；需要在首次引导上验证。

**Morrow 现状**

- 场景 + AI 计划 + 快速添加；手动路径存在，但用户要先理解「场景 / 提醒项 / 间隔 / 时段」。
- 同一时刻只启用一个场景；没有模板，也没有「没有 Key 也能先跑起来」的路径。

**机会**

做「零配置起步」：内置场景模板 + 三步首次引导 + AI 可选；让用户先得到一套可编辑的计划，再决定是否接 AI。这不会破坏差异化，反而让差异化被用上。

### P7 工作日 / 节假日 / 午休不敏感

**证据（中弱）**

- 久坐时间 App Store 评论：「希望国家节假日也能设置，否则放假了也像上班那样疯狂提醒」。
- 中文办公场景的常识：午休、调休、节假日与固定工作日不一致。

**Morrow 现状**

- 只有静默时段（默认 22:00–08:00）；没有工作日历、午休、调休 / 节假日。

**机会**

做「工作日历」：周一至周五 + 手动例外 + 午休静默；默认不联网，节假日数据可手动维护。中国本地化差异，国际竞品通常不做。

### P8 通知可靠性 / 权限

**证据（中）**

- Shui #28：「windows设置了到了时间没有任何提醒」。
- 中文 App Store 评论有「所有通知都打开了，就没提醒过一次」的说法（移动端，桌面端不完全可比）。
- Morrow 依赖系统通知、强提醒、首页卡片三条通道；打包 / 签名 / 权限不满足时通知按钮不可用。

**Morrow 现状**

- 通知带完成 / 推迟按钮；首页待处理卡片是可靠通道；强提醒默认开。
- 没有首次启动的通知自检，也没有「为什么没提醒」的诊断。

**机会**

做「通知自检」：首次启动发一条测试通知，显示权限 / 专注 / 签名状态；失败时明确降级到首页卡片。低成本，补信任。

## 三、Morrow 现状对照

### 3.1 已经领先、不要丢的

- **多屏强提醒**：Stretchly 的多屏支持长期是讨论点（#117）；Morrow 主屏完整、副屏简化，覆盖所有显示器。
- **暂停原因可见 + 自动恢复 + 顺延不补发**：Stretchly #413 / #1120 的反例是「暂停了还弹」或「退出会议后永久暂停」；Morrow 的设计更可靠。
- **中文会议应用原生识别**：腾讯会议、飞书、钉钉在国际竞品里通常缺失。
- **本地优先、无账号、无广告**：中文用户对广告 / 会员墙的反弹很强（护眼宝、喝水时间评论）。
- **通知按钮 + 首页待处理卡片 + 强提醒三通道**；休息模式内置引导。
- **没有严格模式**：符合温和陪伴定位，不要照搬 Stretchly 的严格模式。
- **中文界面**：LookAway 用户评论里明确请求中文。

### 3.2 平手 / 已补齐

六路免打扰、菜单栏、今日统计、连续天数、休息闭环、多屏、专注 / 日历（macOS）、一次性提醒、快速添加、数据库导出 / 恢复。

### 3.3 缺口

- 演示 / 共享屏幕隐身与捕获排除。
- 自然停顿顺延。
- 7 天 / 周报。
- 场景模板 / 首次引导 / AI 可选。
- 连续跳过的温和反馈。
- 工作日历 / 午休。
- 长休息 / 可配置时长。
- 通知自检。
- 专注 / 番茄协同。
- 浏览器会议识别（技术风险，不承诺）。
- Windows 专注 / 日历（平台限制，如实降级）。

## 四、功能候选

### 4.1 评分

排序标准：**痛点强度 × 差异化潜力**；成本 / 风险只在同分时裁决。评分是启发式，不是精确公式。

| 候选 | 解决的痛点 | 痛点强度 | 差异化潜力 | 成本 / 风险 | 建议 |
|---|---|---|---|---|---|
| **A. 会议 / 演示隐身** | P1、P3 | 5 | 5 | 4 | **P0** |
| **B. 自然停顿顺延** | P2 | 5 | 4 | 2 | **P0** |
| **C. 零配置场景模板 + 首次引导** | P6 | 4 | 5 | 3 | **P1（紧随 P0）** |
| **D. 轻量周报 / 7 天趋势** | P5 | 3 | 4 | 2 | P1 |
| **E. 节奏自适应（连续跳过反馈）** | P4 | 4 | 4 | 3 | P1 |
| **F. 工作日历 / 午休** | P7 | 3 | 3 | 2 | P2 |
| **G. 长休息 / 可配置时长** | 竞品平手项 | 2 | 3 | 2 | P2 |
| **H. 通知自检 / 权限诊断** | P8 | 3 | 2 | 1 | P2 |
| **I. 专注 / 番茄协同** | 邻近替代 | 3 | 4 | 4 | P2 |

> C 的差异化潜力很高，但痛点是「用不上」而不是「被打断」，且证据里有推断成分；建议在 A+B 之后立刻做，不要挤进同一张 spec。

### 4.2 P0 候选

#### A. 会议 / 演示隐身（暂名「演示模式」）

**用户故事**：我在共享屏幕或开会时，不希望同事看到桌宠、遮罩或提醒；会后自动恢复。

**范围**

1. 菜单栏 / 全局快捷键进入「演示模式」：暂停提醒、隐藏宠物与气泡、抑制强提醒，菜单栏显示状态。
2. 会议应用前台或全屏时，宠物气泡建议「要进入演示模式吗？」；不自动进入，避免误判。
3. **捕获排除**：宠物 / 遮罩窗口在系统允许时排除屏幕捕获（macOS `NSWindow.sharingType = .none`；Windows `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)`），作为「检测失败」的安全网。
4. 会后恢复：会议 / 全屏结束自动退出；也可手动退出；可选「再安静 N 分钟」。
5. 暂停原因 + 一键纠正：菜单栏显示「演示中 / 会议中 / 你手动暂停」；如果没自动暂停，用户可一键「刚才该暂停」并在本地留日志。

**边界**

- 不读屏幕内容、不读窗口标题、不检测摄像头；只使用前台应用身份、全屏几何与用户主动操作。
- 不做「共享的是哪个窗口」的识别，不承诺浏览器会议 100% 命中。
- 保持「温和」：不强制、不锁屏、不做严格模式。

**证据**

Stretchly #1479、#969、#1120、#355；中文同类会议适配缺口；Morrow 桌宠 / 遮罩无捕获排除（机制推导）。

**验收**

- 模拟共享屏幕：观看看不到桌宠、气泡、遮罩与提醒。
- 演示模式下提醒不投递、不积压；退出后按原间隔恢复。
- 菜单栏状态与实际一致；任意一路信号失败时能手动兜底。
- 不读取屏幕内容；捕获排除不可用时明确降级，不静默失败。

**风险**

- 共享屏幕检测的可靠性；捕获排除 API 的平台支持需要 spike。
- 自动建议可能打扰；默认手动 + 建议，自动进入需用户显式开启。

#### B. 自然停顿顺延

**用户故事**：我正在打字 / 拖拽，不想被全屏提醒打断；希望等我停下来再提醒。

**范围**

1. 周期性提醒到点时，若最近 5 秒内有键鼠输入，最多顺延 60 秒；在第一个安静时刻投递。
2. 顺延超过上限仍持续输入：降级为宠物气泡 / 菜单栏提示，不弹全屏；提醒进入待处理，不丢。
3. 一次性提醒保持绝对时刻语义，不顺延（遵守 ADR 0001）。
4. 设置项：顺延上限 0 / 30 / 60 秒；默认 60 秒；可关闭。
5. 宠物状态：「等你停下」；恢复后正常提醒。

**证据**

Stretchly #189；LookAway「等待合适时机」；Morrow 固定网格 + 强提醒默认全屏。

**验收**

- 连续打字时不再出现全屏弹窗；停手后提醒出现。
- 顺延有上限；不会无限拖到下一次；不补发、不积压。
- 一次性提醒不受影响；行为与 ADR 0001 一致。
- 设置可关闭；日志能解释「为什么晚了几十秒」。

**风险**

- 长时间持续输入的用户可能永远等不到安静时刻；用上限 + 降级兜底。
- 与「强提醒必须处理」的定位有张力；需要明确「什么时候降级为气泡」。

### 4.3 P1 候选

#### C. 零配置场景模板 + 首次引导

- **用户故事**：我不想申请 API Key，也想在 2 分钟内得到一套可用的计划。
- **范围**：3–5 个内置模板（久坐程序员、会议密集日、备考冲刺、居家办公、护眼优先）；三步首次引导（工作时段 / 最想解决的两件事 / 选模板）；模板生成后可编辑；AI 作为「自定义」入口保留。
- **AI 可选**：保留 DeepSeek 默认端点，增加国内常用提供商预设与连接测试；明确说明费用与数据只发送用户主动输入的内容。
- **边界**：模板是确定性内容，不调用 AI；不写医疗建议；不做多场景同时启用。
- **验收**：新用户无 Key 也能在 2 分钟内得到计划；AI 路径不回归；模板可删除 / 重选；不联网也能完成。
- **风险**：模板内容维护；「一键模板」可能让用户跳过对场景的理解；需要真实首次使用测试。
- **证据**：产品事实（BYOK）+ 中文桌面工具缺场景 + 少数派 / App Inn 的自建与付费吐槽；BYOK 门槛本身是推断，需验证。

#### D. 轻量周报 / 7 天趋势

- **用户故事**：我想知道这周到底有没有改善，而不是只看今天。
- **范围**：7 天完成 / 跳过 / 推迟；连续达标天数；宠物生长回顾；菜单栏「本周完成 x/y」；可选导出。全部本地。
- **边界**：不做独立仪表盘、不做云端、不做排行榜；一次性提醒不计入每日目标（沿用现有语义）。
- **验收**：数字与 CheckIn 一致；无新增遥测；不改变今日统计语义。
- **风险**：数据量与时区；视觉上不要变成「报表」。

#### E. 节奏自适应（连续跳过反馈）

- **用户故事**：我连续跳过时，不希望被更多提醒轰炸，也不希望被强制。
- **范围**：连续跳过 / 推迟 3 次后，宠物询问「现在不方便？暂停 30 分钟 / 降低频率 / 继续」；用户选择后才改变节奏；每天重置；本地日志。
- **边界**：不自动隐藏、不做严格模式、不做愧疚式文案。
- **验收**：不选就不改变；可关闭；不增加提醒频率；与智能免打扰不冲突。
- **风险**：问得太频繁会变成新的打扰；需要克制的触发条件。

### 4.4 P2 候选

- **F. 工作日历 / 午休**：周一至周五 + 手动例外 + 午休静默；默认不联网；节假日可手动维护。解决「放假还疯狂提醒」。
- **G. 长休息 / 可配置时长**：在微休息之外提供 5–10 分钟长休息；可配置 stand / move / rest 时长。竞品已有，Morrow 目前固定 60–180 秒。
- **H. 通知自检 / 权限诊断**：首次启动测试通知；显示通知、强提醒、专注 / 日历权限状态；失败时明确降级到首页卡片。
- **I. 专注 / 番茄协同**：检测 macOS Focus 或番茄会话，在开始 / 结束边界安排休息；不读取内容，不做另一个番茄钟。

### 4.5 本轮明确不做

- **摄像头在场 / 眨眼检测**：与本地优先冲突，见 ADR 0004。
- **严格模式 / 强制不可跳过**：竞品有反弹；与温和陪伴定位冲突。
- **云端账号 / 同步**：破坏本地优先；本轮不引入。
- **AI 现场生成休息内容**：保持内置确定性内容，避免医疗建议与不可审校输出。
- **社交 / 排行榜 / 愧疚式提醒**：会把陪伴变成压力。
- **移动端 / 手表 App**：本轮聚焦桌面；手表是替代品，不是当前交付目标。
- **读取窗口标题 / 屏幕内容 / 日历事件标题**：隐私边界之外。
- **广告 / 订阅墙**：中文用户对广告与会员墙反弹强；本地优先是差异。
- **团队 / 企业看板**：不是当前用户场景。
- **多场景同时启用**：保持「同一时刻一个场景」的模型；模板只做切换，不改变模型。
- **通用应用白名单 / 黑名单**：误判成本高；优先用会议应用身份 + 全屏 + 用户手动兜底。

## 五、推荐顺序与验证

### 5.1 建议

- **第一张 spec：A + B 合并为「不被打断」切片。** 两者都改「投递与可见性」，共享暂停状态、宠物状态与菜单栏文案；A 解决「被看见」，B 解决「时机不对」。
- **第二张 spec：C「第一次上手」。** 让没有 API Key 的用户也能得到可用计划；否则 A+B 做得再好，差异化仍被门槛挡住。
- **第三张：D / E。** 用一到两周自用数据决定先做周报还是节奏自适应；不要同时做。
- **P2 按自用反馈挑选，不一次性铺开。**

### 5.2 验证方式

不引入遥测，只用本地数据与自用观察：

- 模拟共享屏幕（Zoom / 飞书 / 腾讯会议）时，桌宠、气泡、遮罩是否对观看者不可见。
- 连续打字场景下，全屏弹窗是否消失；顺延是否在上限内。
- 跳过 / 推迟次数是否较基线下降；连续跳过后的自适应提示是否被接受。
- 无 Key 首次使用能否在 2 分钟内完成一套计划。
- 周报是否被打开、是否帮助用户说出「这周哪里变好了」。

### 5.3 待验证的技术点

- macOS / Windows 的窗口捕获排除 API 在 Wails v3 透明置顶窗口上的可行性。
- 共享屏幕检测能做到什么程度；做不到时，手动演示模式 + 捕获排除是否足够。
- 输入活跃度检测能否复用现有空闲检测，而不引入新权限。
- 浏览器会议识别是否值得投入；如果只能靠全屏，文案不要承诺。

## 六、证据质量与缺口

- **强**：Stretchly GitHub issues（已抽查 #1479 / #969 / #1120 / #355 / #189 / #1366 / #266 的标题、状态与日期）；Morrow 代码事实。
- **中**：App Store 评论（样本小、1 星偏差）；中文社区帖（作者自述、样本小）；竞品官方文档（厂商立场）。
- **弱 / 推断**：中文「桌宠在共享屏幕里被看见」没有找到一手原话，是由窗口捕获机制推导；BYOK 门槛是产品事实 + 推断；中文同类功能细节来自商店页 / 宣传文，未实测。
- **缺口**：V2EX / 知乎 / 小红书 / 酷安 / 贴吧 / B 站评论未系统抓取；没有用户访谈、留存或弃用数据；Morrow 尚未定价。
- **建议**：锁定 A 之前，用真实共享屏幕做一次 30 分钟手工验证；锁定 C 之前，找一位非技术用户做一次无 Key 首次使用测试。
