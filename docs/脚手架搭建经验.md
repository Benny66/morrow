# 脚手架基座搭建经验（从 base/ 提炼，供 Electron+TS 新基座复用）

> 本文是 `base/` 脚手架在搭建过程中沉淀下来的**可复用工程方法论**总结。
> 用途：从 0 搭建新的 Wails v2 + Vue3 + Vite + Element Plus + Go 客户端工具基座时，作为"该搬什么、怎么搬"的指南。
>
> 核心立场一句话：**这个基座最值钱的不是代码，是"把工程约定编译成会失败的检查"这套方法论。**
> 代码会因为换语言、换框架、换通信模型而作废，方法论不会。

---

## 0. 先分清：能搬 vs 要重写

新基座（纯工具，无登录/RBAC，删 h5/uniapp）意味着大量前提被推翻，
但有一批"DNA"是跨语言、跨框架的。开干之前先分类：

| 资产 | 类别 | 说明 |
|---|---|---|
| 架构护栏（guard 测试 + ESLint 规则） | ✅ 搬方法论，重写实现 | 思想原样搬，实现从 go/parser 换成 TS AST / ESLint |
| 依赖登记制（deps.yaml） | ✅ 几乎原样搬 | 与语言无关，只是校验器换语言 |
| 黄金范例 + 代码生成器 | ✅ 搬方法论 | 模板内容全换，锚点注入/幂等/fail-fast 手法保留 |
| 单一真相（single source of truth） | ✅ 搬原则 | 每个规则只写一处，其余共同引用 |
| 宪法文档（AGENTS.md + CLAUDE.md） | ✅ 搬结构 | 内容换成 IPC / main-renderer 约定 |
| 统一命令入口（Makefile） | ✅ 搬 | target 内容换 |
| 冒烟测试 | ✅ 搬 | 断言内容从 HTTP 登录换成 IPC 握手 |
| OpenSpec 治理 | ✅ 搬 | 直接沿用 |
| Go 三层 + HTTP 响应协议 + JWT/RBAC | ❌ 丢弃 | 换成 main 进程 + IPC 通道 + 无鉴权 |
| 多端（mobile/miniapp）与品牌登录页 | ❌ 丢弃 | 单端 Electron |

---

## 1. 核心理念：把"约定"编译成"会红的检查"

这是整个基座最有价值的一条。**软约束（写在文档里的规矩）一定会被违反**，尤其当 AI
参与生成代码时。解法是把约定变成 CI 里会变红的静态检查，让"违反"在 build/lint 阶段
就暴露，而不是等到 code review 或线上故障。

具体落到两类机制：

- **后端护栏**：Go 的 `go test` 里放 `internal/guard/` 包，用 `go/parser + go/ast`
  解析源码做结构化断言（分层越界、响应协议、模型注册等）。
- **前端护栏**：根 `eslint.config.js` + 自定义 ESLint 规则（如 `menu-group.js`），
  用 ESLint 的 AST 接口做断言。

新基座（TS 单语言）反而更简单：**只用一套 ESLint + vitest 就够了**，不需要 Go 侧再
造一个 AST 轮子。`electron-vite` 下用 `vitest` 跑"架构护栏"测试，用自定义 ESLint
规则做"导入/命名/结构"类约束。

### 1.1 最重要的护栏铁律：护栏必须"感知自己瞎了"

这是从真实事故里长出来的教训，比护栏本身更重要：

> **当解析器解析不到任何东西时，必须 `Fatal`/报错，而不是当作"通过"静默放行。**

否则护栏会"瞎掉"——代码写法一变，正则/AST 匹配失效，护栏从"拦违规"退化成"永远绿"，
还给你一种"很安全"的错觉。

三个真实例子（都写进了 guard 的注释里）：

1. `frontend_store_test.go`：解析 Pinia store 成员时，若解析到 0 个成员，**Fatal** 而非
   当空集合继续（否则所有引用都误报，或当通过就瞎了）。
2. `permission_registry_test.go`：解析 router 权限码与 initBaseData 权限码，任一为空
   **Fatal**（否则正则失效时静默放行）。
3. `menu-group.js`：AST 找不到 `routes` 数组时，**report 报错**而非跳过。

**搬到新基座的落点**：任何"用正则/AST 解析源码来断言"的护栏，第一行判断必须是
`if (解析结果为空) throw`，并附一句"写法可能已变更，请同步更新护栏解析规则"。

## 2. 单一真相（Single Source of Truth）

一条规则只允许有一个出处，其余所有消费者（生成器、护栏、文档）都引用它，禁止
"各写一份"——写两处就一定会漂移。

base/ 里的典型：

- `backend/scripts/pluralize.sh`：复数化规则（s/x/z/ch/sh→+es…）的唯一真相，被
  `gen-module.sh`（生成器）和 `guard`（护栏测试）共同调用，注释里明确写"不要在别处
  另写一套规则"。
- `go.mod` 的 `module` 声明：guard 用 `readModuleName()` 从 go.mod 动态读，不硬编码
  `base-backend`，这样 `make init` 改名后护栏不拆。
- `contracts/openapi.yaml`：字段/响应形状的唯一真相。
- `deps.yaml`：依赖清单的唯一真相。

**搬到新基座**：TS 项目里，把"命名规则""IPC 通道前缀""依赖清单"各自落到一个脚本/文件，
生成器与 lint 规则共同 import，而不是复制粘贴。

---

## 3. 依赖登记制（deps.yaml）

新增依赖不能只 `npm install`，必须在 `deps.yaml` 登记并附一句理由。护栏做**双向校验**：

- 正向：清单里每个直接依赖（`package.json` 的 `dependencies`，跳过 `devDependencies`）
  都必须在登记表里（漏登记 → 红）。
- 反向：登记表里每个条目都必须真实存在于清单（僵尸条目 / 拼写错误 → 红）。

这个模式与语言无关，新基座可直接搬：一个 `deps.yaml` + 一个解析 `package.json` 的
vitest 用例做双向断言即可。登记时多问一句"这是不是可跨工具复用的通用依赖"，业务专属
逻辑别进基座。

---

## 4. 黄金范例 + 代码生成器

### 4.1 唯一范例，禁止模仿历史模块

base/ 里一个很关键的决策：**系统管理五件套是"可运行的能力"，但不是"代码范例"**——
范例唯一指向 `backend/_example/`。原因写在注释里：五件套是历史代码，已经互相漂移，
照它写会学到坏味道。

新基座同样要有这一条：**第一个真实工具 ≠ 范例模板**。工具会越写越具体，模板必须
保持最小、干净、带 `// TODO` 锚点。

### 4.2 生成器的手法是资产，模板内容不是

`gen-module.sh` 里的工程手法值得原样搬：

1. **锚点注入**：在目标文件里放 `【gen:routes】`、`【gen:migrate】`、`【gen:permissions】`
   这类注释锚点，生成器靠 `grep -qF` 定位注入位置。锚点既给生成器用，也给护栏测试用
   （护栏断言锚点存在），删了会两边一起坏——这是刻意的耦合。
2. **fail-fast 前置校验**：动任何文件前，先把"锚点是否存在""资源是否已被占用"全部查完。
   否则中途失败会留下"后端已生成、前端未注入"的不一致状态，重跑又被幂等检查拦住。
3. **幂等 / 拒绝覆盖**：目标文件已存在就报错（`require_new`），绝不覆盖用户业务代码。
4. **`// TODO` 锚点**：生成的文件带 `// TODO: 业务逻辑`，AI/人只填锚点处。
5. **占位符替换**：`Example`/`example` → 目标模块 PascalCase/snake_case，用 sed 替换，
   避开 `sed -i` 的平台差异。

**搬到新基座**：Electron 工具基座里"工具"就是模块，做一个 `make gen name=<tool>`，
模板换成 `ipcMain handler + preload 桥接 + renderer 页面` 三段，同样用锚点注入 +
幂等 + TODO。

## 5. 分层纪律，用 AST 护栏强制执行

base/ 后端是 `controller → service → model` 三层，护栏用 AST 断言"层与层不越界"：

- `services/` 不得 `import gin`（服务层不碰 HTTP 语义）。
- `controllers/` 不得 `import gorm` 或 `database`（控制器不直接操作 DB）。
- `controllers/` 不得手写 `c.JSON`（响应必须走统一 `utils/response`）。
- models 里每个内嵌 `BaseModel` 的结构体必须注册进 `AutoMigrate`，双向校验防 typo。

**搬到新基座**（Electron 的分层是另一种形态）：

```
renderer (Vue3/React)  ──IPC──▶  preload (contextBridge)  ──▶  main (Node)
```

对应的护栏可以写成 ESLint 规则：

- renderer 层禁止 `import` 任何 `node:*` / `fs` / `child_process`（必须走 preload 暴露
  的受控 API，安全隔离）。
- main 层禁止 `import` 任何 `.vue` / UI 组件。
- IPC 通道名必须登记在一张表里，preload 与 main 双向引用，防通道名拼写漂移。

这条经验的名字叫"**用静态检查锁死边界**"，三层的具体划分不重要，重要的是"边界必须
可被机器验证"。

## 6. 宪法文档分层（AGENTS.md + 域 CLAUDE.md）

文档也分两层，职责清晰：

- **根 `AGENTS.md`**：跨端通用铁律（目录命名、依赖登记、干净性、验证入口）。
- **域 `CLAUDE.md`**：就近规则（`backend/CLAUDE.md` 管 Go 三层，`frontend/CLAUDE.md`
  管 Vue 规范），AI 在哪个目录干活就读哪份。

两条值得搬的细节：

1. **⚙️ 标记**：能被机器强制执行的规则，在文档里标 `⚙️`，并指向对应的护栏
   （"该规则由 eslint.config.js 编译成会失败的检查"）。这样读者一眼知道哪些是软约束、
   哪些是硬约束。
2. **`docs/map.md` 导航地图**：告诉 AI"哪类代码在哪个文件，先读它"，避免 `find` 盲扫。
   "上下文最优"的关键是知道去哪读，而不是全局加载。

新基座保留这个结构即可：根 `AGENTS.md`（IPC 安全、依赖登记、干净性）+ `main/`、
`preload/`、`renderer/` 各自的域宪法 + 一份 `docs/map.md`。

## 7. 统一命令入口（Makefile）

AI 和人只记 `make <target>`，不记零散脚本路径：

```make
make test      # 护栏测试
make lint      # 静态检查
make smoke     # 冒烟
make gen       # 生成新模块
make dev       # 并行启动
make package   # 打包
```

新基座照搬这个思想。Electron 下 `make package` 对应 `electron-builder`，`make dev`
对应 `electron-vite dev`，`make smoke` 对应启动 Electron 主进程跑一遍 IPC 握手。

---

## 8. 冒烟测试：把"能跑"变成可观察事实

`smoke.sh` 的做法是：构建 → 随机端口 + 临时 DB 启动 → 登录拿 token → 命中受保护路由
→ 断言 → 清理。目标是防"启动即崩"，让"完成了"有客观证据，而不是嘴上说。

新基座对应的冒烟：`electron .`（或 headless）启动 → 断言 main 进程起来 → 通过 preload
发一个 ping 通道 → 断言返回 → 退出。同样用 `trap cleanup EXIT` 保证不残留。

---

## 9. 配置三层 + 可配置化

配置体系是"默认值 → YAML → 环境变量"逐层覆盖。品牌（名称/logo/背景）可配置，
不硬编码字符串——前端所有标题从 `/system/info` 拉，`index.html` 的 `<title>` 是中性
占位，运行时覆盖。

新基座同理：工具基座的"工具列表""窗口尺寸""数据目录"都应走配置，禁止在代码里
硬编码标识性字符串（护栏可加一条"禁硬编码品牌/工具名"）。

---

## 10. 工程治理（OpenSpec）

base/ 全程用 OpenSpec 管理变更（`openspec/changes/` + `openspec/specs/`），每个功能
都有 proposal → spec → 实现 → 归档的闭环。新基座从第一天就接入，比事后补强得多。
这套 `openspec-governance-pro` skill 本身可直接复用。

---

## 11. 干净性

`.gitignore` 必须挡住运行时产物：`*.db`、`dist/`、`node_modules/`、`*.exe`、
`*.orig`、`*.rej`、vite 时间戳缓存。新基座额外要挡 Electron 产物：`out/`、`release/`、
`*.asar`。

---

## 12. 一句话迁移地图（Go 多端 → Electron 单端）

| base/ 的形态 | 新基座的形态 |
|---|---|
| Go `controller→service→model` 三层 | `main(TS) → preload → renderer` 三层 |
| HTTP 路由 + 统一响应 `{code,message,data}` | IPC 通道 + 统一 `{ok, data, error}` 返回 |
| JWT / RBAC / 操作日志中间件 | 无（纯工具，无鉴权） |
| guard 测试（go/parser AST） | vitest + ESLint 自定义规则 |
| `deps.yaml` 双向校验 | 原样搬，校验器换 TS |
| `_example/` + `gen-module.sh` | `_example/` + `gen-tool.sh` |
| `make gen name=asset` 生成三层+路由+权限 | `make gen name=<tool>` 生成 ipc+preload+页面 |
| 多端（frontend/mobile/miniapp） | 单端 Electron |
| 品牌登录页 + 四端品牌下发 | 单窗口 + 工具列表配置 |
| `make smoke`（HTTP 登录冒烟） | `make smoke`（IPC 握手冒烟） |
| OpenSpec 治理 | OpenSpec 治理（直接沿用） |

## 附：从 0 搭建新基座的建议顺序

1. 先立"宪法"：根 `AGENTS.md` + 域 `CLAUDE.md` + `docs/map.md`（哪怕先空着，结构先定）。
2. 再接 OpenSpec，把本文当成第一个 change 的输入。
3. 搭 `electron-vite + vue-ts`（或 react-ts）最小可跑，`make dev`/`make package` 通。
4. 立护栏框架：一条 ESLint 规则（renderer 禁 import node 模块）+ 一个 vitest 护栏用例，
   先把"护栏要能感知自己瞎了"这条落地。
5. 立依赖登记制 + `deps.yaml` 双向校验。
6. 做第一个真实工具，然后从它提炼 `_example/` 模板 + `make gen`。
7. 补冒烟测试与打包。

> 顺序的关键：**护栏和治理先于业务工具**。护栏早期只有一两条，但越早立，后面
> 每个工具都长在纪律里，而不是最后再回头补。
