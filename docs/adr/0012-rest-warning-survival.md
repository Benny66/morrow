# 休息预警的存活判据是"目标触发是否落定"，不是时间

实机观察到：stand 提醒每 45 分钟一条，预警本应只在到点前亮 60 秒，宠物气泡却连续挂了
20 多分钟「1 分钟后该起身拉伸了」。根因是 `tickWarnings` 为了覆盖"目标时刻已到但这轮
tick 还没投递"的空窗，把"预警目标时刻已过"当作**保留**预警的条件，而这个空窗没有任何上限：
那一次 fire 只要没有转成倒计时（顺延到上限转安静投递、暂停期被 claim 成 silent、静默时段、
真实休息后静默跳过），预警就永远停在 warning 态；又因为 `EnterWarning` 只接受 idle，
这条僵尸状态还会挡住之后所有正常的预警，让 Remaining 恒为 0、文案永远停在「1 分钟后」。

决定：**预警的存活判据从"时间"换成"事实"**——它预告的那次触发仍待投递时它才活着；
该触发以任一终态落定（安静投递 / 暂停静默 / 静默时段 / 休息后跳过 / 错过）立即撤销；
进入智能免打扰时同样立即撤销，解除后按新的下一触发重新判断。顺延中的触发**不算落定**，
所以打字期间预警可以多活几十秒。措辞一并从写死的一句改为按真实剩余分三档，
宠物气泡与菜单栏共用同一个函数出处。

## 备选方案

- **给时间宽限加一个上限**（如 fire 后 2 个 tick 强制撤销）：改动最小，但暂停期间
  `tickWarnings` 整轮不跑，上限根本没机会被检查——这次事故恰好发生在锁屏；
  四类落定分支的行为还会各不相同。
- **只把预警气泡的优先级降到暂停气泡之下**：一行 CSS 级改动，但后台状态仍是 warning，
  菜单栏与 `GetRestModeSnapshot` 继续对外说谎，属于用 UI 掩盖数据错误。
- **文案逐秒倒计时**：最准确，但宠物窗口按 4 秒轮询快照，要做秒级就得加密轮询；
  菜单栏那行会每秒变化 → 每秒重建 NSMenu，正是当初加"文本没变就不重建"要避免的抖动。
- **顺带放宽安静投递**（让它在预警消失前也能进休息模式）：会重开
  「打字时不打断」的既有裁决，本次不动。

## 后果

- 预警的存活从此绑定在一个持久事实上，而不是本机时钟：休眠、改系统时间、tick 被拖长
  都不会让它误撤销或误保留。
- 「预警亮了一分钟 → 只有一张待处理卡片」是安静投递路径的**预期**结果，不是回归；
  对持续打字的用户，这个落差会比以前更明显（以前是气泡不消失，现在是气泡消失后没下文）。
- 这类失效没有症状——不崩、不报错、日志干净，只有 UI 上一句永远对不上的话。
  按 AGENTS.md 铁律 5，必须编译成会红的检查：四类"不转倒计时的落定"分支各一条引擎测试，
  外加一条「无候选触发时预警不得存活」的不变量测试。
- 三档 × 四个 kind 分支让预警文案从 4 句变成 12 句，必须集中在 restmode 包的单一函数里，
  否则气泡与菜单栏必然漂移（`app.go` 里那句写死的「1 分钟后休息」就是漂移的现有样本）。
