# 更新检查是唯一自动外呼，且只访问 GitHub Releases

Morrow 的隐私口径一直是「数据只留本机，除可选 AI 调用外不发起网络请求」。
但 issue #2 暴露了另一面：用户停在 v1.1.0，v1.1.1 的白屏修复如果没人手动去
Releases 下载，就永远送不到他手里。决定新增**自动更新检查**：默认开启、可在设置里
关闭，只读取 GitHub Releases 的版本元数据（tag、说明、发布页地址），不携带任何用户
数据；发现新版本只在宠物气泡（气泡链最低优先级）与设置页版本行提示，M1 不下载、
不替换安装包。

## 备选方案

- **仅手动检查**：完全保持现有隐私承诺，但设置页里的按钮大多数用户不会点，
  解决不了「修复版没人知道」这个原始痛点。
- **首次启动询问是否自动检查**：隐私上更严谨，但多一步引导、拒绝率不可控，
  且拒绝后仍然回到手动检查的老问题。
- **直接做完整自动更新（下载 + 替换 + 重启）**：需要重做发布资产（macOS 的
  `.app.zip`、Windows 的裸 `.exe`）、自定义资产匹配与可选签名校验，验证面显著更大；
  先用「检查 + 提示」验证价值，再决定是否进入 M2。

## 后果

- README 与设置页必须如实写明：这是应用**唯一**的自动网络请求，只访问
  GitHub Releases，不上传任何数据；关闭自动检查后不再发起该请求。
- 自动检查失败要静默（只记日志），否则离线/网络受限用户会反复看到报错；
  手动检查失败必须显式反馈。
- 更新提示是宠物气泡优先级的最低一级，永不压过提醒与休息流程；用户忽略某个
  版本后，该版本不再冒泡，但设置页仍显示可更新。
- 若后续进入 M2，可复用同一份「可用版本」状态，但下载/安装/回滚属于另一套
  资产与校验设计，不能把 M1 的检查结果直接当作可安装产物。
