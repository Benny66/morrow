# 做一个桌面宠物，真正难的不是画它

> 上一篇写了 Wails v2 升 v3 的全过程，这篇写副产品：那只趴在桌面上的宠物。
> 项目：**https://github.com/Benny66/morrow**

---

## 先交代一下这东西长什么样

一只叫「小满」的宠物，一滴水，头顶长了株芽。你每完成一次喝水或者起身，芽就长一点。

它不是一张贴图，是个真窗口：

- 240×380 的逻辑像素，全透明，无边框，浮在所有窗口之上
- 宠物本体 192×208，剩下的空间留给它头顶的气泡
- 能拖，能贴边藏起来，鼠标划过再露出来
- 屏幕共享和录屏的时候，它不出现在画面里
- 气泡一冒头，窗口会临时长高；气泡没了，缩回去

听起来像个小玩具。我原本也以为是。

结果这一个窗口吃掉的时间，比主窗口还多。它还干过一件我完全没想到的事——**偷吃鼠标点击**。

原因很简单：**主窗口是个正常的窗口，宠物窗口不是。** 它的边界随时在变、它要盖住别人的窗口、它的透明区域还得能被点穿。每一条都在跟操作系统和框架的默认假设对着干。

这篇讲的就是这些坎，全是踩出来的，不是查文档查出来的。

---

## 一、先把「窗口有几种形态」这件事定死

做挂件最容易走歪的一步，是把窗口当成一个固定尺寸的画布，然后在里面挪东西。

一旦你这么做，后面全是补丁。

我一开始就只允许两种形态：

| 形态 | 尺寸（1.0 倍） | 什么时候 |
|---|---|---|
| 基础 | 240×380 | 平时 |
| 气泡 | 宽 240，高按实测 | 有话说的时候 |

**没有第三种。** 出现第三种，说明设计没想清楚。

### 高度不是拍的，是加出来的

先拆一下窗口里到底装了哪些东西。

窗口里除了 208 高的宠物，上面还有气泡：场景名、标题、最多两行正文、两个按钮，加一条尾巴。

而宠物那一块是 `justify-content: flex-end` + `overflow: hidden`——**内容超出是从顶部裁掉的**。

所以高度不够的症状特别讨厌：气泡的标题被切掉半行，`overflow: hidden` 一声不吭，你看着界面只会觉得「这个样式是不是没生效」。

我中途加了一行场景名，12px × 1.4 ≈ 17px，加上间距 20px，于是 360 变成 380。原来那个 360 本来就是"刚好够"，实测下来气泡 + 间隙 + 宠物 + 内边距 ≈ 359.6。

差 0.4px 也能用，但只够用一版。

### 为什么不让窗口常驻大尺寸

最省事的做法：不管缩放多少，窗口一律按 1.0 倍留足气泡空间。

我否了。理由是**透明窗口的透明区域照样吃鼠标事件**。

这一条是整篇文章的地基，后面还会反复出现：

> 你以为透明 = 看不见 = 没影响。实际上透明 = 看不见，但**依然挡着**。

0.5 倍缩放时宠物只有 96×104，却占着一个 240×380 的窗口。剩下那一大片区域，用户点桌面图标点不着、框选拖不动。他不会骂你的设计，只会觉得"我电脑怎么有点卡卡的"。

那反过来，让气泡的字号跟着缩放等比变小呢？

0.5 倍的时候字号只剩 6–7px。放得下，但读不了。

最后选的是第三条路：**窗口临时变大**。代价是要处理窗口尺寸变化带来的一堆连锁反应，收益是平时不占地方。这笔账我觉得划算。

### 顺便说一下这窗口是怎么来的

宠物窗口和主窗口用的是**同一份前端产物**。

打包时 `dist` 用 `//go:embed` 塞进 Go 二进制，不会为宠物单独打一份。区分靠 URL：

```go
URL: "/#/pet"
```

`Pet.vue` 这条路由挂了 `meta.bare: true`，`App.vue` 看到它就只渲染 `router-view`，跳过侧栏和标题栏——不然一个 240 宽的小窗里会画出整个后台界面。

还有一条：**窗口是平级的，不是子窗口。** 宠物要浮在别的应用之上，子窗口做不到。

## 二、扩窗：四条规则和一个反算

扩窗这事儿，写起来就十几行，但我给它单独开了个文件，而且**不带任何窗口对象**：纯函数，输入矩形，输出矩形。

原因后面会说。先看规则。

### 规则一：底边不动，横向以宠物中心对称

不能让窗口"往右上角长"。

宠物是用户摆在那儿的，气泡一冒出来它自己往上跳二十像素，视觉上就是"宠物在躲我"。

扩窗的锚点就定在**底边中点**：底边 y 不变，横向围绕中心左右各长一半。

三行代码：

```go
centerX := base.X + base.W/2
x := centerX - w/2
y := base.Y + base.H - h
```

### 规则二：不能缩得比基础尺寸还小

气泡内容很少的时候，算出来的窗口可能比基础窗口还矮。这时候必须夹回去。不然宠物本体就被裁掉半截。

### 规则三：不能超出工作区

宽度超了就往内收，高度超了就钉住顶边（宠物的底边跟着下移，相当于临时往下挪了一下）。

这里有个坑：**判断"贴着屏幕右缘"必须用屏幕的 WorkArea，不能用 Bounds。**

Bounds 包含菜单栏和 Dock 占的那一条。用它算，宠物会藏到 Dock 底下去，用户只能看见一条尾巴。

### 规则四：反复调用不能越算越大

前端每次气泡可见性变化都会重报一次高度。如果 `petBubbleRect` 不是幂等的，第二遍会拿扩过的矩形当基准，再扩一次，第三遍再扩……

结果是窗口每帧长高一点，肉眼看到的是宠物缓慢往下沉。这个 bug 特别难查，因为每一步都"看起来正确"。

### 一个反算

扩窗之后，窗口矩形已经不代表用户把宠物放在哪了。

于是需要反算回基础矩形：

```go
func petBaseRect(cur petRect, baseW, baseH int) petRect {
    x := cur.X + (cur.W-baseW)/2
    y := cur.Y + cur.H - baseH
    return petRect{X: x, Y: y, W: baseW, H: baseH}
}
```

两个地方非用它不可：

1. **退出时持久化。** 用户退出时可能正挂着一条提醒，窗口是扩着的。存扩出来的坐标，下次启动宠物就凭空下移一段。
2. **贴边吸附的判断。** 程序化扩窗也会改窗口位置，如果拿窗口矩形去比"用户是不是拖动过"，气泡一出现就会被误判成拖动。

第二条坑了我一次，症状是：气泡弹出的瞬间，宠物被吸到屏幕边上藏起来了。

### 为什么是纯函数

因为我要能这样测：

```go
func TestPetBubbleRectAnchorsBottom(t *testing.T) {
    base := petRect{X: 1000, Y: 600, W: 120, H: 190}
    work := petRect{X: 0, Y: 0, W: 1440, H: 900}
    got := petBubbleRect(base, 240, 276, work)
    want := petRect{X: 940, Y: 514, W: 240, H: 276}
    ...
}
```

不用启动应用，不用开窗口，`go test` 一秒跑完。9 个测试，锁死了底边锚定、右缘夹取、顶边钉死、下限、宽高上限、副屏原点、反算、幂等。

其中副屏那条最值得说：

```go
work := petRect{X: 1512, Y: 0, W: 1440, H: 900}   // 副屏原点不是 0
```

单屏开发的人永远写不出这条测试，因为他的世界里屏幕原点永远是 (0,0)。

**这就是纯函数的真正价值：它让"我没想到还有一种情况"变成一条能写下来的断言。**

## 三、透明窗口会吃掉你的鼠标

回到刚才那句话：透明 ≠ 点穿。

这事的后果比想象中严重，因为它悄悄改变了产品设计。

### 贴边收起，不能靠 CSS

想要"宠物贴到屏幕边，只露半张脸"的效果，最直觉的做法是给宠物加个 `transform: translateX(-220px)`。

宠物视觉上藏起来了。但窗口还在原地，240×380 那块区域依然归它，鼠标点上去什么都不会发生。

用户在那一块区域上点不到桌面、点不到图标、拖不动框选。而屏幕上什么都没有。

**一个看不见的死区，比一个看得见的宠物烦人一百倍。**

我的做法是：**真的把窗口移出屏幕**，只留 20px 在屏幕内。

```go
case x-wa.X <= petDockThresholdPx:
    return "left", wa.X - width + petDockPeekPx, y
```

窗口的大部分跑到屏幕外，点不到的地方从 240 宽缩到 20 宽。剩下那 20px 是必须付的过路费。要让鼠标能划过来触发"展开"，总得留点地方。

你可能会问：为什么不干脆让整个窗口穿透，把 `pointer-events: none` 全设上？

因为那是两件事。`pointer-events` 只作用在 DOM 层，管的是"网页里哪个元素收这一下"；而窗口占多大一块屏幕、要不要把点击交给下面的应用，是原生窗口的事。要让窗口范围也穿透，得走系统级 API（macOS 上是 `ignoresMouseEvents`）。

而这个开关和"可拖动"直接打架：窗口不接收鼠标事件，你也拖不动它了。

所以宁可把窗口真的移出屏幕，也不去动那个开关。

### 露出来的那 20px，前端怎么摆

后端把窗口移出去了，可宠物本体在窗口里的位置没变。于是用户看到的是"宠物不见了，屏幕上有一条空白"。

得让宠物在视觉上平移到露出的那条边里。

我一开始想用手算一个固定偏移量，`translateX(-220px)` 那种。算到一半发现：**窗口尺寸会随缩放设置变**（0.5 到 2.0），硬算出来的偏移量迟早错一截。

改成 flex 对齐：

```css
/* 藏在左边 → 露出的是窗口右缘 → 宠物靠右 */
.pet--dock-left { align-items: flex-end; }
/* 藏在右边 → 露出左缘 → 宠物靠左 */
.pet--dock-right { align-items: flex-start; }
```

宠物自己会跑到正确的位置，跟窗口多宽没关系。

这是个很典型的取舍：**能不写数字的地方就别写数字。** 数字会被别处的变化搞坏，而约束不会。

顺带一句：那个 20px，Go 侧叫 `petDockPeekPx`，前端叫 `PET_DOCK_PEEK_PX`。两边写不一样会怎样？露出来半张脸，或者露出来一片空白。都不报错。

于是加了个镜像校验，改一边不同步另一边，测试红。

## 四、一个 SVG 让你拖不动宠物

这是整篇文章里我最想讲的一段，因为它花了我最久。

### 症状

窗口没有标题栏（透明窗口本来就不该有），拖整个窗口就是移动它的方式。`.pet` 这一层已经声明了 `--wails-draggable: drag`，所以拖内边距、拖空白处都正常。

**一压到宠物身上，拖不动。**

### 三层错误嵌套

我一开始以为是 CSS 属性没生效，加了 `--wails-draggable: drag`，没用。

去翻 wails 注入的 `drag.ts`，核心是这段：

```js
function isDraggableEvent(event) {
  const target = eventTarget(event);
  const style  = window.getComputedStyle(target);
  return style.getPropertyValue('--wails-draggable').trim() === 'drag'
    && event.offsetX >= 0 && event.offsetX < target.clientWidth
    && event.offsetY >= 0 && event.offsetY < target.clientHeight;
}
```

第一层：自定义属性会继承，所以写在父容器上"应该"能传下去。值确实传到了。

第二层：`eventTarget()` 里，如果命中的不是 HTMLElement，**只往上找一层** `parentElement`。

第三层，也是最关键的：光标压在宠物身上时，最内层命中的是 SVG 的 `<circle>` / `<ellipse>` / `<path>`。它们不是 HTMLElement，`eventTarget()` 上溯一层拿到的是 SVG 的 `<g>`——**而 SVG 的几何元素没有 CSS 布局盒，`clientWidth` 和 `clientHeight` 恒为 0。**

于是最后一条判定 `event.offsetX < target.clientWidth` 退化成 `offsetX < 0`，而光标压在宠物身上时 `offsetX` 明明是正数，直接判假。

三条判定，卡在最后一条。

### 「SVG 元素 clientWidth 恒为 0」这个结论怎么来的

不是猜的。

我一开始也看到网上有种说法：WebKit 上 SVG 元素读不到继承来的自定义属性。

这个解释不对，但它和另一个错误结论（"属性没继承"）会导致完全一样的排查方向，特别容易走偏。

最后我翻了 WebKit 的 `Source/WebCore/dom/Element.cpp`。`clientWidth()` 里根本没有 SVG 分支，只有：

```cpp
if (CheckedPtr renderer = renderBox()) {
    return convertToNonSubpixelValue(...renderer->paddingBoxWidth()...);
}
return 0;
```

`<circle>` / `<g>` 渲染成 `RenderSVGShape` / `RenderSVGContainer`，都不是 `RenderBox`，`renderBox()` 为空，直接 `return 0`。

到这里才叫查清楚了。

顺带说一句：不管上面哪种解释成立，修法都一样：**让命中点不再是 SVG 元素**。其实不用先判定到底是哪一个，能省两小时。

### 修法

关键不在给容器加宽高。`.pet__art` 是个普通 div，本来就有布局盒、有真实宽高。出问题的是**里面的 SVG 还在吃指针事件**：

```css
.pet__art {
  position: relative;
  --wails-draggable: drag;   /* 第二重保险：万一继承值被某层覆盖成空 */
}
.pet__svg {
  width: 100%;
  height: 100%;
  pointer-events: none;      /* 命中点不再落在 <circle>/<g> 上 */
}
```

加上 `pointer-events: none` 之后，光标压在宠物身上，`event.target` 直接就是 `.pet__art`——一个有布局盒、`clientWidth` 是真实宽度的 div。三条判定全部成立。

这个问题值得单开一段，因为它教了我一件事：

> **挡在"能用"和"不能用"之间的，往往不是一行配置，而是一个你没料到的默认假设。**
> 而这类问题的排查，靠试是试不出来的——只能把中间那层源码读一遍。

## 五、点击和拖拽，会抢同一串鼠标事件

修好拖拽之后，新需求来了：点一下宠物，它挥挥手。

听起来是小需求。

### 原生拖拽会把你的 mouseup 吃掉

`drag.ts` 里，鼠标只要移动 1px 就会 `invoke('wails:drag')`，然后进入**系统模态循环**。

进去之后，后续的 `mousemove` 和 `mouseup` 不再投递到页面。

同时它对 `click` / `contextmenu` / `dblclick` 挂了捕获阶段的 `suppressEvent`：只要 `dragging` 为真就掐掉。而 `mouseup` 会先把 `dragging` 置回 false。

于是"拖完之后那次 click 到底传不传得到页面"，取决于 `mouseup` 和原生拖拽会话的时序。两边都不可靠。

### 我的解法，以及它的真实上限

用位移判：

```js
// 按下时记屏幕坐标
pressOriginX = event.screenX
pressOriginY = event.screenY

// 松手时
const dx = event.screenX - pressOriginX
const dy = event.screenY - pressOriginY
if (Math.hypot(dx, dy) > PET_CLICK_MAX_TRAVEL_PX) return  // 4px
onPetClick()
```

坐标必须用 `screenX/screenY`。原生拖拽期间窗口跟着光标走，`clientX` 几乎不变，只有屏幕坐标能反映光标真正走过的距离。

**但这个方案有上限，得说明白。**

它只在 `mouseup` 真的被投递到页面时才跑得到。而原生拖拽 1px 就启动，然后就把 `mouseup` 吞了。

实际跑起来的效果是：**"点一下挥手"只在零位移点击上触发。手抖出 1px，这一轮既没拖，也不会挥手。**

这是那条原生通道的固有限制，不是阈值选得不好。改大改小都变不出第二次机会。

### 两道闸门，缺一不可

还有一种更脏的情况：`mouseup` 永远不来。

原生拖拽启动后进模态循环，页面再也收不到 `mouseup`。于是"按下"这个状态一直挂着。

而拖动自己的窗口**不会让窗口失焦**——`blur` 兜不住。

结果：几分钟后用户去点气泡上的「完成」，那次 `mouseup` 被当成"这轮手势松手了"，拿着一个几分钟前的基准坐标去算位移。判出来虽然不是点击，但状态机已经脏了一轮。

松手时先过两道闸门：

```js
if (performance.now() - pressAt > PET_PRESS_STALE_MS) {   // 1200ms
  cancelPetPress(); return;                                // 过期，只清状态
}
const dragged = petDragged;   // mousemove 里就已置位
```

第一道：过期就不判点击。第二道：`petDragged` 在 `mousemove` 里就置位了，哪怕窗口跟着光标走、看起来位移很小，也不会把拖动误判成点击。

### 留一条备用轮胎

这条路是在赌框架的实现，所以我在 `lib/pet.ts` 里留了个开关：

```ts
export const PET_JS_DRAG_FALLBACK: boolean = false
```

打开它，就切到方案 B：用 `Window.Position()` / `Window.SetPosition()` 在前端自己搬窗口，绕开 wails 的命中测试。`mousemove` 里用 `rAF` 节流，每帧最多一次 IPC（Retina 上 `mousemove` 一秒几百条，逐条搬窗口又费往返又抖）。

**两条通道必须互斥。** 原生拖拽一旦启动就进系统模态循环，会把兜底要用的 `mousemove` 掐断，同时开着只会互相覆盖。

类型那里还有个细节，我特意写成 `: boolean` 而不是让它推导成字面量 `false`：

```ts
export const PET_JS_DRAG_FALLBACK: boolean = false   // 不是 = false 就完事
```

不这么写，TS 的类型收窄会把 `if (PET_JS_DRAG_FALLBACK)` 整段当成死代码，而它恰恰是这条兜底通道唯一的入口。改成 `true` 的时候还会被当成恒假分支处理掉。

一个 `: boolean`，救的是三个月后改这个开关的人。

## 六、坐标有三套，别混着用

这一节最闷，但也是最容易埋雷的。

### 建窗的 X/Y 和 SetPosition 的 X/Y 不是一回事

`WebviewWindowOptions` 里的 `X` / `Y`，是**相对某块屏幕的 WorkArea 原点**。

而 `Position()` / `SetPosition()` 用的是**全局逻辑坐标**。

混用会怎样？

多屏的时候，你的宠物每次启动都被拽回主屏。

因为：保存下来的是全局坐标，恢复时却被当成相对坐标解释。副屏原点如果是 (1512, 0)，你存的全局 (1536, 700) 会被理解成"主屏原点 + 1536,700"，直接跑出屏幕。

这个 bug 只在多屏上现形。单屏开发的人永远不会遇到。

**我的解法是干脆不用建窗的 `X` / `Y`：** `InitialPosition` 也不设，位置统一在窗口创建之后用 `SetPosition` 设一次。少一套坐标，就少一半错的可能。

### 位置回落：什么算「还算看得见」

配置里存的位置，下次启动时可能已经完全无效了：拔了副屏、改了分辨率、换了个更大的 Dock。

如果直接把窗口放到一个不存在的坐标上，用户看到的是：**宠物没了，而且没有任何界面能把它找回来。**

得先判断"这个位置还算可见"：

```go
if x+width > wa.X+petPositionMinVisible &&
   x < wa.X+wa.Width-petPositionMinVisible &&
   ...
```

关键是 `petPositionMinVisible = 48`，而不是要求整窗可见。

48 的意思很朴素：**只要能露出一个能抓住的角，用户就能拖回来。**

要求整窗可见会把"跨两块屏摆放"（一半在左屏一半在右屏）误判成不可见，然后宠物被强行拽回主屏。用户会以为这软件有病。

判不通过就回落到主屏右下角，留 24px 边距，别压 Dock 上。

### 归属哪块屏，两个地方用了两套判据

这不是不一致，是故意的。

**扩窗时，用宠物脚底（底边中点）判归属。**

因为扩窗只往上长，脚底才是用户真正放置宠物的位置。跨屏摆放时，窗口一变大就容易被算到另一块屏去。

**拖动时，用左上角判归属。**

因为拖动中的窗口跟着鼠标，左上角足够明确，也能避免"跨两块屏时被算两次"。

同一个问题，一个用脚底，一个用左上角。想清楚"这个判断是为了什么"，答案自己就出来了。

## 七、怎么分辨「用户拖的」和「我自己挪的」

贴边收起要轮询窗口位置。

但窗口位置也会被我自己改：扩窗、还原、贴边、展开。如果不区分，会进入一个很蠢的循环：气泡一出现，窗口位置变了，我以为用户在拖，判断贴边，把宠物吸走。

### 为什么用轮询而不是事件

v3 有 `events.Common.WindowDidMove`。

我没用。理由很实在：**各平台后端是否稳定 emit，我离线确认不了。**

而 `Position()` 是确定的。

于是 500ms 一轮采样，判据是"连续两次采样位置相同"，等价于"拖动已经停了"。

开销可以忽略：只有在位置变化时才做判断。

### 三道跳过

轮询里连续三个 `continue`，每一个都对应一个实际的 bug：

```go
if a.petDockCollapsed() { continue }   // 收起态窗口在屏幕外，位置是我自己设的
if a.petBubbleExpanded() { continue }  // 扩窗是程序化移动，不是用户拖的
if time.Now().UnixMilli() < a.petDockIgnoreUntil.Load() {
    continue                            // 刚展开的 3 秒内不重新吸附
}
```

第三条最微妙。

宠物展开后，窗口回到的位置**仍然贴着边**——那正是当初触发吸附的地方。不设宽限期，下一轮采样立刻又把它吸走。

症状是：鼠标划过边缘，宠物闪一下又藏回去了。

### 还有第四道：比较基础矩形

刚展开的那 3 秒过了之后呢？如果用户就是不动它，一直停在展开位置，也不该反复吸附。

还有一条：

```go
if a.petDockAtHome(x, y, width, height) { continue }
```

而 `petDockAtHome` 比的是**基础矩形**，不是窗口矩形。

为什么？因为扩窗会改变窗口位置和尺寸。按窗口矩形比，气泡一出现就会被误判成"用户拖动了"。

你看，`petBaseRect` 这个反算函数，出现了第三次。

一个正确的抽象，会在你没想到的地方反复救你。

### 一个不能省的 defer

这个 goroutine 是长驻的：

```go
defer func() {
    if r := recover(); r != nil {
        slog.Error("宠物贴边监测异常退出", "panic", r)
    }
}()
```

它挂了不会有任何界面提示，日志里也只有一行。用户感受到的是"贴边功能突然不好使了"。

长驻 goroutine 的 panic 必须兜住。不指望靠它撑住继续跑，至少得让日志留下证据。

## 八、还有几个不太起眼但会咬人的地方

### 8fps，不是 4fps

宠物窗口是 Frameless + AlwaysOnTop 的小窗，**启动后通常拿不到键盘焦点**。

也就是说 `document.hasFocus()` 一开始就是 `false`。"失焦"是它的常态，不是例外。

我一开始按"失焦可以慢"给了 4fps。结果是：宠物从第一眼起就一顿一顿的，用户以为功能卡了。

改成 8fps（满帧 12 的 2/3）。真正省电的那一半浏览器已经给了：窗口不可见时 `rAF` 自动暂停。

**不要把常态当成异常去优化。** 这条规则不止适用于帧率。

### 4 秒轮询

宠物窗口和主窗是两个 webview。用户在设置页换了宠物形象或缩放，宠物窗口收不到通知。

正解是发个事件。但契约里宠物域只有一个 Dock 动作（贴边收展用的），为了"换个形象"再加一套域常量，我觉得不值。

所以用了一次极廉价的本地绑定调用轮询，4 秒一次，读内存里的配置。换个形象这种低频操作，4 秒延迟完全可以接受。

**能用丑办法解决的低频需求，就别动契约。** 契约一膨胀，后面每条校验都要跟着改。

### 录屏时它得消失

宠物窗口设了 `ContentProtectionEnabled: true`。屏幕共享、录屏的时候看不到它，自己屏幕上还看得见。

macOS 和 Windows 有实现，Linux 是 no-op。

所以 UI 上必须如实降级，不能假装支持。我单独写了一行函数在编译期判定平台，而不是启动时探测——**能力是编译期决定的，探测只会多一条可能失败的路径。**

## 九、这套东西怎么验证

宠物窗口不好测：它没有业务逻辑，全是几何和时序。

我把能抽出来的都抽出来了。

| 层 | 怎么测 | 覆盖什么 |
|---|---|---|
| 几何纯函数 | 9 个 `go test` | 锚定、夹取、上限下限、副屏原点、反算、幂等 |
| 前后端契约 | 镜像校验 | 20px 露出宽度两边一致 |
| 真实窗口 | 手测 | 拖动、贴边、多屏、录屏 |

第一层最值钱。它不用启动应用、不用开窗口、不用管平台，一秒跑完。

第二层是防我自己：改了 Go 没同步前端，测试红。这类漂移不会有任何症状，只会在某天表现为"露出来半张脸"。

第三层只能手测。多屏、录屏、缩放这几件事，做自动化的成本比收益高，我算过一次，不值。

## 最后三句

1. **桌面挂件的难点从来不在"画"。** 透明、命中测试、坐标、程序化移动。这四件事跟"宠物长什么样"一点关系都没有，但它们决定这东西能不能用。

2. **每一个坑的解药，都藏在"我以为的默认行为"和"实际的默认行为"之间。** 透明不等于点穿，SVG 没有布局盒，原生拖拽会吞掉 mouseup，建窗坐标和 `SetPosition` 不是一套。没一条是文档写在前面的。

3. **所以多花点时间，把能变成纯函数的部分抽出来。** 几何抽出来，9 个测试锁死；契约抽出来，镜像校验锁死。剩下的时序问题只能手测，但至少你不用同时怀疑几何和时序——**排查最贵的从来不是修，是不知道问题在哪一层。**
