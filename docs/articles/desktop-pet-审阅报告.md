## 一、已修的硬伤（3 处，必改）

### 1. CSS 是编的

初稿里我写了：

```css
.pet__art {
  position: relative;
  width: 100%;      /* ← 源码里没有这两行 */
  height: 100%;
  --wails-draggable: drag;
}
```

回查 `Pet.vue` 第 1690 行，真实的 `.pet__art` 只有 `position/flex/display/align-items/justify-content/cursor` 加 `--wails-draggable`，**没有 width/height**。

而且我加这两行是有害的：`.pet__art` 是 flex 子项（`flex: none`），给它 `width: 100%` 会让它撑满整行，宠物居中位置和气泡测量的基准全变。读者照抄会把布局搞坏。

**已改成真实样式**，并把解释改成"关键不在加宽高，而在别让 SVG 吃指针事件"——这才是源码注释里的真实修法。

### 2. Go 代码里有个不存在的变量

初稿：

```go
if now < a.petDockIgnoreUntil.Load() { continue }   // now 从哪来的？
```

源码是 `time.Now().UnixMilli()`。这是编译器直接报错的级别。

已改成完整写法（三行 if，因为原代码是跨行块）。

### 3. 同一节自相矛盾

第四节开头说"拖宠物本体是唯一的移动方式"，隔一段又说"拖窗口的空白区域能动"。

两句都是我写的。事实是：`.pet` 整层都声明了 `--wails-draggable: drag`，所以内边距、空白处、宠物本体**理论上**都能拖，只是宠物本体那条被 SVG 的命中问题堵死了。

已改成："拖整个窗口就是移动它的方式……所以拖内边距、拖空白处都正常。**一压到宠物身上，拖不动。**"

## 四、我独立核实过的一条

整篇文章最重的技术论据是"SVG 元素 `clientWidth` 恒为 0"。初稿只是转述项目注释。

我查了 WebKit 上游 `Source/WebCore/dom/Element.cpp`：

```cpp
int Element::clientWidth() {
    ...
    if (RenderBox* rend = renderBox()) return adjustForAbsoluteZoom(rend->clientWidth(), rend);
    return 0;
}
```

确实没有 SVG 分支。`RenderSVGShape` / `RenderSVGContainer` 不是 `RenderBox`，`renderBox()` 返回空，直接走到 `return 0`。**论据成立，可以放心发。**

顺带确认了另一层：`event.target` 命中的 `<circle>` 是 `SVGElement` 不是 `HTMLElement`，所以 `eventTarget()` 会走 `parentElement` 分支拿到 `<g>`——文章的描述准确。
