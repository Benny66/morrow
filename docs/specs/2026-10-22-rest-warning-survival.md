# 休息预警存活判据与三档措辞 — 规格说明书

> 术语见 `CONTEXT.md` 的「休息预警（Rest Warning）」「预警措辞（Warning Wording）」「自然停顿顺延」。
> 取舍与被否决的方案见 `docs/adr/0012-rest-warning-survival.md`。
> 本 spec 的用户故事编号前缀 **WS**（Warning Survival），与 baseline-parity 的 `US-*` 不冲突。

## 1. 问题陈述

stand / move / rest 三类提醒应当在到点前 1 分钟给出一条**只告知、不打断**的预警（宠物气泡 +
菜单栏一行）。实际行为是：预警一旦发出就常常撤不掉。

实机证据（2026-10-22，`/Applications/Morrow.app`，用户配置 45 分钟一条「起身活动」）：
17:15 那条 stand 落在锁屏暂停里，触发点被占用成 `silent`（`reminder_fires` id=62，`fired_at=0`），
而预警从 17:14 起一直挂在「1 分钟后该起身拉伸了」——到 17:38 已挂了 23 分钟，而下一条 fire 在 18:00，
预警窗口根本没开。当天 8 次 stand 到点里有 7 次走的是「顺延到上限 → 安静投递」。

根因在 `internal/reminder/engine.go:327-339`：为了让「目标时刻已到但这轮 tick 还没投递」的
0–20 秒空窗不闪断，代码把"目标时刻已过"当成**保留**预警的条件，而这个保留没有上限。
只要那次触发没有转成倒计时，预警就永远停在 `warning` 态。四类分支都会走到这里：

| 分支 | 位置 | 为什么没进倒计时 |
| --- | --- | --- |
| 顺延到上限转安静投递 | `engine.go:630`（`!quietDelivery` 才 Enter） | 安静投递刻意不进休息模式 |
| 暂停期的周期点 | `engine.go:257` 暂停时整轮不跑 `tickWarnings`；`:505-512` 落 `silent` | 没人来撤销 |
| 静默时段 | `engine.go:601-609` 早退 | 同上 |
| 真实休息后静默跳过 | `engine.go:546-554` 早退 | 同上 |

僵尸预警还**挡住之后所有正常预警**：`EnterWarning` 只接受 `idle`（`machine.go:162-167`），
于是后续预警建不起来，`RemainingSec` 恒为 0，文案永远停在「1 分钟后」。

第二个缺陷独立于卡死：`machine.go:309-319` 的四句措辞是写死的，即便链路正常，
剩余 20 秒和剩余 8 秒显示的仍是「1 分钟后」；`app.go:1228` 菜单栏那句「1 分钟后休息」是第二份手写文案。

值得解决的理由：这条链路是休息模式的**开场**，它出错时用户看到的是一个说谎的宠物，
而说谎持续二十分钟——比完全不提醒更伤信任。

## 2. 方案概述

### 2.1 总体形状

把预警的存活判据从**时间**换成**事实**：预警预告的那次投递还没有落定，它才继续活着。

```
预警存活 = 未被暂停
           ∧ 目标提醒项仍是当前启用场景里启用中的 rest 提醒
           ∧ 目标触发点 (reminder_id, planned_fire_at) 尚未被占用
```

三条里后两条今天已经能在 `tickWarnings` 的循环内就地算出（候选集合本来就构建了一遍，
占用情况用引擎现有的内存备忘 `Engine.isClaimed`），不需要新的查询接缝。
判据不成立 → 本轮 `CancelWarning()`，不再有"目标时刻已过就先留着"的分支。

措辞改为按真实剩余分三档，且**只存在于 `internal/restmode` 的一个函数里**；
宠物气泡与菜单栏都取这个函数的返回值。

### 2.2 接缝（deep module）

整套改动只跨**一个**接缝：`Engine.Tick()` 驱动、`restmode.Machine` 对外可见的状态与快照。

| 接缝 | 用途 | 现状 |
| --- | --- | --- |
| `Engine.Tick()` + `Machine.State()/Current()` | 断言预警的存活/撤销时机 | 已有（`engine_warning_test.go`） |
| `Machine.Snapshot().CueText / RemainingSec` | 断言三档措辞 | 已有（`warning_test.go`） |
| `fakeStore.claimed`（模拟唯一索引） | 让测试把"触发点已落定"摆成事实 | 已有（`schedule_test.go:294-376`） |
| `a.trayStatusText()` | 断言菜单栏取自同一函数 | 已有 app 层测试构造能力（`app_presentation_test.go:185`） |
| `internal/guard/` AST 护栏 | 锁死"措辞只有一处出处" | 复用现有护栏包 |

**不新增任何前端镜像逻辑**：措辞一律服务端算好经 `Snapshot.CueText` 下发，
前端仍只渲染（AGENTS.md 铁律 1；`frontend/src/lib/restmode.ts` 头部注释已写明"只镜像常量与类型"）。

### 2.3 保活的真实作用域（原稿说错了一处，以注入实验为准）

原稿把"`tickWarnings` 必须先于 `tickGrid`"写成判据成立的前提，并要求一条会红的顺序测试。
实现时两次注入推翻了这一点：

- **注入 B2（无候选一律撤销，等价于把顺序反过来让 claim 先发生）**：只有
  `TestWarningSurvivesWhileDeferring` 变红，到点那轮仍然是 `countdown`——
  因为 `Enter` 同时接受 `idle`，撤销后重建看不出差别。
- **注入 A2（时间宽限 80 秒，足够跨过顺延窗口）**：安静投递、停用、静默时段、
  休息后跳过四条全部变红。

结论：**判据只读"是否已被占用"这一事实，与两个函数的先后无关**。
保活真正保护的是**跨多轮 tick 的顺延窗口**（触发点会连续 2–3 轮不被占用），
撤销它就等于在用户毫无预告的情况下让覆盖层凭空出现。
到点那一轮不闪断只是顺带的好处，不是一条契约。

### 2.4 显示生效路径（不改，仅供验收对照）

- 菜单栏：每秒 `tickRestMode` → `refreshTrayIfChanged`（`app.go:1122`），文本没变不重建 NSMenu。
- 宠物：每 4 秒 `GetRestModeSnapshot`（`Pet.vue:762`，`PET_SETTINGS_POLL_MS=4000`）。
- 覆盖层：`Alert.vue` 仅在"窗口可见 && 有待处理"时每秒刷新快照（`:151-190`），预警期不刷。
  撤销生效对宠物最迟 4 秒、对菜单栏最迟 1 秒，这是可接受的既有粒度，本 spec 不加密轮询。

## 3. 用户故事

### A. 存活判据：四类落定都要撤销预警

- **WS-1** 正常路径不变：距某条 rest 提醒的触发点 ≤60 秒且 >0 秒时，
  宠物气泡与菜单栏各出现一次预警；到点后进入倒计时覆盖层（今天正确的行为，不许回归）。
- **WS-2** 顺延到上限转安静投递：预警的目标点在 `quiet_delivery` 下被占用后，
  下一轮 tick 预警撤销；气泡与菜单栏回到原有优先级（待处理卡片照常存在）。
- **WS-3** 真实休息后静默跳过（`shouldSkipStandMove`）：目标点落成 `silent` 后，
  下一轮 tick 预警撤销。
- **WS-4** 静默时段到点：目标点被 `dispatch` 早退落 `silent` 后，下一轮 tick 预警撤销。
- **WS-5** 顺延仍在排队（目标点**未**被占用、用户还在输入）：预警**继续存活**，
  即使已经越过计划时刻最多一个顺延上限（默认 30 秒，可配 60 秒）。
  这是刻意保留的：顺延不改变"下一分钟真的会弹"的承诺。
- **WS-6** 时钟恰好走到计划时刻的那一轮：正常路径必须直接进入倒计时，不因为预警的
  存取时机而丢会话（这条只断言终态，见 §2.3——它锁不住调用顺序）。
- **WS-7** 预警发出后该提醒项被停用或删除、或启用场景被切换/停用：
  判据第二条不成立 → 下一轮 tick 预警撤销（**即使目标时刻已经过去**，
  这条正是今天撤不掉的第二种形态）。
- **WS-8** 预警撤销后，之后任何一条 rest 提醒进入 60 秒窗口时能**重新预警**
  （僵尸态不再挡住新预警）。

### B. 暂停：立即撤销，恢复后重扫

- **WS-9** 预警存活期间进入智能免打扰（锁屏 / 会议 / 全屏 / 空闲 / 专注 / 日历任一）：
  该轮 tick 立即撤销预警，不等目标点落定。
- **WS-10** 暂停期间不得产生新预警（保持现有"暂停不预警"的语义）。
- **WS-11** 暂停解除后的第一轮 tick：按当时真实的 60 秒窗口重新判断，
  窗口内有待投递触发就预警，没有就保持安静。
- **WS-12** 预警导致的"暂停气泡被遮住"消失：`Pet.vue` 的优先级链仍是
  陪做 > 预警 > 顺延 > 演示建议 > 暂停 > 待处理 > 久坐软提醒，
  但因为暂停时预警已撤销，用户看到的是「屏幕已锁定，我先不打扰」而不是假预警。

### C. 措辞：三档 + 单一出处

- **WS-13** 预警文案按真实剩余分三档：`>30s` / `>10s 且 ≤30s` / `≤10s`（含 0 秒的空窗）。
  第三档一律用"马上…"，**剩余 ≤10 秒时不得再出现"1 分钟后"**。
- **WS-14** 三档 × 四类 kind 分支（stand / move / rest / 兜底）共 12 句，全部集中在
  `internal/restmode` 的同一个措辞函数里；建议措辞（实现可微调，但不得跨档改写语义）：

  | kind | >30s | ≤30s | ≤10s |
  | --- | --- | --- | --- |
  | stand | 1 分钟后该起身拉伸了 | 半分钟后该起身拉伸了 | 马上该起身拉伸了 |
  | move | 1 分钟后该走动一下了 | 半分钟后该走动一下了 | 马上该走动一下了 |
  | rest | 1 分钟后让眼睛休息一下 | 半分钟后让眼睛休息一下 | 马上让眼睛休息一下 |
  | 兜底 | 1 分钟后开始休息 | 半分钟后开始休息 | 马上开始休息 |

- **WS-15** 菜单栏顶部那行直接用同一个函数的返回值，删除 `app.go:1228` 里写死的「1 分钟后休息」。
  一次预警最多让 NSMenu 重建 2 次（60→30、30→10 两个边界），不引入逐秒抖动。
- **WS-16** `Snapshot()` 内先算 `RemainingSec` 再算 `CueText`（现顺序 `machine.go:293-301` 是反的），
  且 `TotalSec` 仍为 60、`State`/`Kind` 等字段语义不变。
- **WS-17** 倒计时（`countdown`）阶段的引导动作文案与时长不变——本次只动预警阶段。

### D. 契约、护栏与文档

- **WS-18** `internal/guard/` 新增一条 AST/文本护栏：形如「N 分钟后…」「半分钟后…」「马上…」的
  预警措辞字面量**只允许出现在 `internal/restmode`**；在 `app.go`、`frontend/src` 等处命中即为红。
  按铁律 5，护栏在 `internal/restmode` 内解析到 0 条措辞时必须报错（"写法可能已变更，请同步更新护栏解析规则"）。
- **WS-19** Go 与前端之间不新增镜像：`RestModeState` 六态与 `WarningLeadTime` 的对账由
  现有 `guard/parity_test.go` 继续覆盖；措辞不进镜像（铁律 1）。
- **WS-20** 注释与文档同步：`machine.go:29-31`、`machine.go:44-48`（`WarningLeadTime` 的理由）、
  `engine.go:254-257` 与 `:275-282`（判据从时间换成落定）、
  `frontend/src/lib/restmode.ts` 头部对 `warning` 状态的描述（现在写着"显示「1 分钟后…」气泡"）。
  `CONTEXT.md` 与 `docs/adr/0012-rest-warning-survival.md` 本轮已写好，实现时校对一遍引用路径。

## 4. 已定决策

| # | 决策 | 否决的备选 |
| --- | --- | --- |
| D-1 | 存活判据 = 目标触发点仍待投递（占用即撤销），不是时间宽限 | fire 后固定宽限 N 秒；保留预警只改文案 |
| D-2 | 进入暂停立即撤销，解除后重扫 | 保留到恢复后直接进倒计时；只降气泡优先级 |
| D-3 | 措辞三档（>30 / ≤30 / ≤10） | 沿用写死的一句；逐秒倒计时 |
| D-4 | 顺延期间预警优先，不做文案叠加 | 顺延即撤销预警；气泡叠加"你在输入" |
| D-5 | 安静投递仍不进休息模式，待处理卡片兜住 | 让安静投递也弹覆盖层（重开既有裁决）；调低顺延上限 |
| D-6 | 菜单栏与气泡共用同一措辞函数 | 菜单栏保留固定一句；菜单栏逐秒 |
| D-7 | 「该点是否已占用」继续用引擎内存备忘，不新增 DB 查询 | 加 `Store.IsFireSettled`（见 §7 的已知代价） |

## 6. 明确不做

- 不改安静投递的投递形态（仍不弹覆盖层、仍进待处理卡片）。
- 不改自然停顿顺延的上限、默认值与"输入停止即投递"的行为。
- 不做逐秒倒计时文案，不为措辞加密宠物轮询频率。
- 不改 `WarningLeadTime`（仍 60 秒）与休息时长/引导动作内容。
- 不重排宠物气泡优先级链（预警仍排在顺延气泡之上）。
- 不新增 `Store` 方法、不动 `reminder_fires` 表结构与唯一索引。
- 不引入前端第二份预警文案逻辑；不改 `RestModeState` 枚举。
- 不处理"多类提醒同一时刻到点只预警其中一条"的选择偏好（沿用 `tickWarnings` 现有取最早点的规则）。
- 不动 ADR 0009–0011 已确认的久坐时钟、画像隐私边界与默认人格。

## 7. 补充说明

**已知代价（诚实记录）**：D-7 用内存备忘作判据，而备忘在跨自然日时被 `rollDay` 清空
（`engine.go:673-683`）。极端情形——rest 提醒的触发点正好压在 00:00 且预警在前一分钟发出——
撤销会晚一个 tick（≤20 秒），随后同一轮 `tickGrid` 重新占用即自愈。
不为此加 DB 查询：代价是每轮一次 SELECT，收益是 20 秒的尾部，不成比例。
实现时这条不是留在文档里：`TestWarningClearedWithinOneTickAfterMemoCleared` 用"DB 有行、内存备忘为空"
的组合把它钉成用例，并断言尾部**不超过一个 tick**（能跨日切的只有 00:00 这个点，
它仍属于新一天的 FirePoints，会被重放并写回备忘）。

**为什么这个失效必须配护栏**：它不崩、不报错、日志干净（`tickWarnings` 全程没有一行日志），
唯一的症状是 UI 上一句永远对不上的话。按 AGENTS.md 铁律 5，这类"没有症状的失效"要编译成会红的检查。
顺带建议给 `tickWarnings` 加一条 `slog.Info`（进入/撤销各一条，带 reminder_id 与 planned_fire_at），
否则下次同类排查仍然只能靠猜。

**现网遗留**：当前 `/Applications/Morrow.app` 的僵尸预警只活在内存里，重启即清；
