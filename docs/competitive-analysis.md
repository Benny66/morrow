# 竞品差异分析与功能优化（2026-10）

> 第二轮分析见 `docs/competitive-analysis-round2.md`（目标用户收窄为中文办公人群，含痛点证据与功能候选）；本文保留为第一轮记录。

> 范围：泛办公健康（久坐办公人群的喝水、起身、护眼、呼吸等日常保健提醒）。
> 目标：先补齐竞品共同具备的基础能力，再保留并强化 Morrow 的差异化组合。
> 相关决策：`docs/adr/0003-general-office-wellness.md`、`0004-smart-pause-local-signals-only.md`、`0005-p1-busy-free-only.md`。

## 结论先行

1. **竞品的共同下限已经变了**：2026 年的桌面健康提醒工具，普遍具备「空闲/会议自动暂停、休息引导、菜单栏入口、统计」中的至少两项；只做「定时弹窗 + 跳过/推迟」已经不够。
2. **Morrow 的差异不在提醒本身**，而在三件事的组合：自然语言场景 → 整套计划、桌面宠物承载进度、本地优先无账号。竞品要么是单点计时器（Stretchly、Time Out），要么是移动端记录本（WaterMinder、Medisafe），没有人把「多健康域编排 + 环境化陪伴」做在桌面上。
3. **本轮先补基础能力，但不能补成另一款 Stretchly**：智能免打扰、休息模式、菜单栏与多屏提醒都要长在宠物/场景载体上；摄像头、严格模式、云端统计不跟。
4. **交付分两期**：P0 做智能免打扰 + 场景化休息模式 + 菜单栏 + 多屏强提醒；P1 做系统专注与日历忙闲，且只读布尔状态。

## 竞品给我们的四个信号

### 1. 「不打扰」比「提醒得准」更稀缺

Stretchly 的空闲自动暂停、LookAway 的会议/共享/媒体自动暂停，都是用户口碑里最被认可的能力。健康提醒的失败通常不是漏提醒，而是**在该安静的时候响了**。Morrow 目前只有场景启停与静默时段，缺少对环境的基本感知。

### 2. 「收到提醒」不等于「真的休息」

Viraam / LookAway / CareDesk 都在提醒之后提供动作或休息界面。Morrow 的全屏强提醒只解决了「看见」，没有解决「接下来做什么」。把强提醒升级为休息模式，是补齐闭环的关键。
### 3. 桌面入口决定日常触碰频率

竞品普遍有菜单栏/托盘常驻入口；Morrow 的托盘菜单目前只有「显示/退出」，今日进度与下一条提醒要打开主窗才能看到。多屏用户还会遇到强提醒只盖主屏的问题。

### 4. 差异化的护城河仍然是「场景 + 宠物 + 本地」

竞品没有自然语言场景生成，也没有情感化载体；移动端记录本则依赖账号与云端。Morrow 不应为了追平基础能力而引入摄像头监控、严格模式或云端统计——那会同时丢失隐私定位与温和陪伴的差异。

## 本轮功能优化决策

### P0（先交付）

| 能力 | 行为定义 | 为什么现在做 | 验收要点 |
|---|---|---|---|
| **智能免打扰** | 空闲/锁屏/休眠、会议应用前台、全屏应用时自动暂停；暂停期间不投递、不生成待处理，恢复后按原间隔重新计时；单点/一次性错过保留「已错过」可见 | 竞品共同下限，直击提醒疲劳 | 会议/离开期间零通知；恢复后无积压轰炸；设置可逐项关闭触发 |
| **场景化休息模式** | stand / move / rest 到点前 1 分钟由宠物气泡与菜单栏预警；到点进入倒计时 + 一条内置引导动作；结束自动记完成，提前结束可选完成或跳过 | 把「看见」升级为「真的休息」，且复用宠物载体 | 三类提醒进入休息模式；water/toilet/custom 保持简单打卡；打卡数据与现有 CheckIn 一致 |
| **菜单栏快捷入口** | 菜单栏显示今日完成/目标、下一条提醒、待处理数；菜单提供打开主窗、查看待处理、退出 | 提升日常触碰频率，不新增常驻窗口 | 状态与实际数据一致；不引入第二套统计逻辑 |
| **多屏强提醒** | 强提醒覆盖所有显示器，而非只盖主屏 | 副屏办公用户不再漏提醒 | 每个显示器都能看到并处理；主屏行为不回归 |

### P1（后续迭代）

| 能力 | 行为定义 | 边界 |
|---|---|---|
| **系统专注联动** | 系统专注开启时暂停，关闭后恢复 | 只读「是否开启」；默认关闭、显式授权；macOS 优先，Windows 无等价能力时保持会议应用识别 |
| **日历忙闲感知** | 当前日历忙碌时暂停，空闲后恢复 | 只读布尔忙闲；不读标题/参与人/备注；默认关闭、显式授权；不进入 AI 提示词 |

### 本轮明确不做

- **手动暂停 15/30/60 分钟**（未入选）：先靠自动触发与逐项开关控制；两周自用观察误判率后再评估。
- **摄像头在场/眨眼检测**：与本地优先定位冲突，见 ADR 0004。
- **严格模式/强制不可跳过**：与陪伴、温和的定位冲突；竞品里的强制休息或限制跳过做法也不应照搬。
- **历史趋势与周报**：CheckIn 已具备数据基础，但本轮优先补交互闭环；统计留到下一轮。
- **AI 生成休息内容**：休息引导使用内置确定性内容，离线、可审校、不产生医疗建议。
- **日历事件标题、屏幕内容分析、云端同步**：隐私边界之外。

## 默认参数（可在实现时微调）

| 项 | 默认值 | 说明 |
|---|---|---|
| 空闲判定 | 连续 5 分钟无键鼠输入 | 设置项可改 3/5/10 分钟；锁屏/休眠立即暂停 |
| 会议应用 | Zoom、Teams、Webex、腾讯会议、飞书、钉钉、FaceTime | 按前台应用身份识别；不读会议内容；浏览器内会议靠全屏兜底 |
| 全屏判定 | 前台窗口铺满当前显示器工作区 | 若 macOS 必须申请屏幕录制权限，只读窗口几何；拒绝则降级 |
| 提前预警 | 提前 60 秒 | 宠物气泡 + 菜单栏，不发系统通知 |
| 休息时长 | rest 60 秒；stand 120 秒；move 180 秒 | 首版固定，后续再评估是否可配置 |
| 恢复策略 | 恢复后按原间隔重新计时 | 不补发、不积压 |
| P1 授权 | 专注/日历默认关闭 | 首次开启时说明「只读忙闲，不读内容」 |

## 风险与未决点

1. **全屏识别权限**：macOS 上读窗口几何是否必须屏幕录制权限需实测；若必须，按 ADR 0004 的补充条款只读几何、不截屏，并在拒绝时降级。
2. **浏览器内会议**：前台应用识别不到 Google Meet / 飞书网页版；全屏信号可覆盖一部分，但无法保证 100%。产品文案不能承诺「所有会议都能识别」。
3. **Windows 降级**：本轮 macOS 完整实现；Windows 先保证空闲、会议应用、托盘与多屏提醒，专注/日历后续补。降级路径必须在 UI 中如实呈现，不能静默缺失。
4. **宠物状态过载**：暂停、预警、休息、待处理、庆祝都挂在宠物上，需限制状态优先级与文案长度，避免宠物变成仪表盘。
5. **休息内容维护**：内置动作先做最小集（每类 1–2 个），后续扩充需内容审校，不能让 AI 现场生成医疗建议。

## 成功判定

连续自用两周，只观察本地数据，不引入遥测：

- 空闲/会议/全屏期间是否零投递；
- 休息模式的完成与跳过比例；
- 跳过/推迟次数是否较基线下降；
- 宠物与菜单栏的暂停状态是否无需解释就能理解。

不设拍脑袋阈值；先建立基线，再决定下一轮是否补手动暂停、统计或严格模式。
